# Migrating from dk.nita.saml20

This guide is for services that use the legacy `dk.nita.saml20` packages from [OIOSAML.Net](https://github.com/digst/OIOSAML.Net) and wishes to move to `DK.Gov.Oio.Saml`. It maps the legacy configuration, endpoints and API to their replacements, lists changes in offered functionality, and describes how to switch a registered service at NemLog-in.

## What changes

| Area               | dk.nita.saml20                                                             | DK.Gov.Oio.Saml                                                                                   |
|--------------------|----------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| Hosting            | ASP.NET (`System.Web`) on .NET Framework 4.7.2, Windows and IIS            | ASP.NET Core on .NET 10 (Windows, Linux, macOS), or ASP.NET MVC 5 with OWIN on .NET Framework     |
| Profiles           | OIOSAML 2 and 3                                                            | OIOSAML 4, and OIOSAML 3 by configuration                                                         |
| Wiring             | HTTP handlers (`.ashx`) and two `Web.config` sections                      | `AddOioSaml` and `AddOioSamlCookieAuthentication`, and an `oiosaml` section in `appsettings.json` |
| Endpoints          | Your choice of paths, e.g. `/login.ashx`                                   | Fixed routes under `/auth`                                                                        |
| Identity providers | Multiple simulteneously supported, with discovery and selection            | Exactly one                                                                                       |
| Signed-in user     | `Saml20Identity.Current`                                                   | `User`, a `ClaimsPrincipal` with one claim per SAML attribute                                     |
| Session            | Own session store and `oiosamlSession` cookie, beside Forms authentication | One authentication cookie, plus the ASP.NET Core session for pending requests                     |
| SP metadata        | Generated by `metadata.ashx` and adapted                                   | Manually adapted from template                                                                    |
| Audit logging      | `IAuditLogger`, e.g. log4net                                               | `Microsoft.Extensions.Logging`, category `DK.Gov.Oio.Saml.Audit`                                  |

## Before you start

- **Choose the integration.** An application on ASP.NET Core uses `DK.Gov.Oio.Saml.AspNetCore`. An ASP.NET MVC 5 application can stay on .NET Framework 4.7.2 or later with `DK.Gov.Oio.Saml.AspNet`, which signs users in with an OWIN cookie ([.NET Framework integration](integration-aspnet.md)). A Web Forms application can use it too, as long as it hosts MVC for the `/auth` endpoints. The steps below name the ASP.NET Core pieces; the .NET Framework guide gives their counterparts.
- **OIOSAML 2 isn't supported.** A service still on OIOSAML 2 must move to OIOSAML 3 or 4 at NemLog-in as part of the update.
- **Run the [sample](sample.md)**. It shows the whole flow and the wiring you're moving to.

## Steps

1. Reference `DK.Gov.Oio.Saml.AspNetCore`, or `DK.Gov.Oio.Saml.AspNet` on .NET Framework, and remove `dk.nita.saml20` and its extensions.
2. Translate the `Federation` and `SAML20Federation` sections to an `oiosaml` section ([Configuration](#configuration)).
3. Register the services and middleware as in the [integration guide](integration.md#registering-the-services), or the [OWIN startup](integration-aspnet.md#startup) on .NET Framework, and delete the `.ashx` handlers and the `forms` authentication element.
4. Replace `Saml20Identity` and login and logout links in your code ([Code](#code)), and any extensions you had ([Extensions](#extensions)).
5. Write new SP metadata with the new endpoint URLs and only AES-GCM encryption, and switch over at NemLog-in ([Switching over at NemLog-in](#switching-over-at-nemlog-in)).
6. Test against the integration test environment, including NemLog-in's integration tests, before production.

## Configuration

Both legacy sections become one `oiosaml` section. The [configuration reference](configuration.md) describes every key.

**`Federation`**

| Legacy                                 | Replacement                                                                                                                         |
|----------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|
| `SigningCertificates`                  | `serviceProvider:certificate`, a single certificate: from a file, the Windows store or code. See [certificates](certificates.md)   |
| `AllowedAudienceUris`                  | Gone: the audience must be `serviceProvider:entityId`                                                                               |
| `SessionTimeout`                       | `session:idleTimeout`, at most 50 minutes, plus `session:maximumLength` (8 hours). See [session lifetime](integration.md#session-lifetime) |
| `AllowedClockSkewMinutes`              | `allowedClockSkew`, a `TimeSpan` such as `"00:03:00"`                                                                              |
| `PreventOpenRedirectAttack`            | Gone: always on. Only a local `ReturnUrl` is followed                                                                              |
| `SessionCookieName`                    | Gone: the cookie names are set through ASP.NET Core's cookie and session options                                                   |
| `MetaDataShaHashingAlgorithm`          | Gone: no metadata is generated                                                                                                      |
| `Actions`                              | See [Extensions](#extensions)                                                                                                       |
| `AuthnRequestAppender`                 | `IAuthnRequestProcessor`, registered in DI                                                                                         |
| `auditLoggingType`, `sessionType`      | See [Extensions](#extensions)                                                                                                       |

**`SAML20Federation`**

| Legacy                                              | Replacement                                                                                                                         |
|-----------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|
| `ServiceProvider` `id`                              | `serviceProvider:entityId`                                                                                                          |
| `ServiceProvider` `server`                          | `serviceProvider:server`                                                                                                            |
| `ServiceEndpoint` `signon`, `logout` `localpath`    | Fixed: `/auth/login`, `/auth/AssertionConsumerService` and `/auth/logout`. See [Endpoints](#endpoints)                              |
| `ServiceEndpoint` `redirectUrl`                     | `serviceProvider:loginRedirectUrl` and `serviceProvider:logoutRedirectUrl`                                                          |
| `ServiceEndpoint` `metadata`, `soaplogout`          | Gone. Metadata generation no longer supported. SOAP logout support is pending.                                                      |
| `IDPEndPoints` `metadata` (a folder)                | `identityProvider:metadataFile` (one file) and `identityProvider:entityId`                                                          |
| `IDPEndPoints` `add` `forceAuthn`, `isPassive`      | `identityProvider:forceAuthn`, `identityProvider:isPassive`                                                                         |
| `IDPEndPoints` `add` `ShaHashingAlgorithm`          | Gone: Now always RSA-SHA256                                                                                                         |
| `IDPEndPoints` `add` `CertificateValidation`        | `ICertificateValidator`. The default checks validity and revocation; see [revocation checking](certificates.md#revocation-checking) |
| `IDPEndPoints` `add` `SSO`, `SLO` bindings and URLs | Gone: Requests now use HTTP-Redirect, and the IdP's endpoints come from its metadata                                                |
| `MinimumNsisLoa`                                    | `levelOfAssurance:minimumNsisLoa`, or `levelOfAssurance:minimumLoa` for every kind of level                                         |
| `AllowAssuranceLevel`, `MinimumAssuranceLevel`      | Gone: These were OIOSAML 2 assurance levels                                                                                         |
| `AppSwitchReturnURL`                                | `appSwitchReturnUrls`, a list of `platform` and `value`                                                                             |
| `RequestedAttributes`, `NameIdFormat`, `ContactPerson`, `Organization` | In your SP metadata file                                                                                                            |
| `ShowError`                                         | Gone: errors are exceptions, shown by your exception handling                                                                       |
| `CommonDomain`                                      | Gone. Common Domain Cookie/Identity Provider Discovery is no longer supported by NemLog-in.                                         |

Choose the profile with `levelOfAssurance:requestGenericLoa`: `true` requests a level as per OIOSAML 4, `false` as per OIOSAML 3 way. It must match how the service is registered at NemLog-in.

It is recommended to keep the SP certificate/key password out of `appsettings.json`; see [paths and secrets](configuration.md#paths-and-secrets).

## Endpoints

| Legacy handler                               | Replacement                                                                                                |
|----------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `Saml20SignonHandler`, e.g. `/login.ashx`    | `/auth/login` starts a login; `/auth/AssertionConsumerService` receives the response                       |
| `Saml20LogoutHandler`, e.g. `/logout.ashx`   | `/auth/logout`, for both your application and the IdP                                                      |
| `Saml20MetadataHandler`                      | None; see [registering the service provider](integration.md#registering-the-service-provider-at-nemlog-in) |
| `Saml20CDCReader`, `Saml20CDCIdPReturnPoint` | None                                                                                                       |

The legacy sign-on handler received the IdP's response on the same path that started the login. Now they're separate, so the assertion consumer service URL in your SP metadata changes.

**Login parameters** change: what a login requires is now configured, not taken from the browser. Set the level of assurance in `levelOfAssurance:minimumLoa`, the profile in `login:profile`, and `forceAuthn`/`isPassive` under `identityProvider` ([configuring what a login requires](integration.md#configuring-what-a-login-requires)). `/auth/login` still takes `ReturnUrl` and `appSwitchPlatform`, plus the new `RelayState`; `cidp` has no equivalent, as there is one IdP. A test SP can still take `forceAuthn`, `isPassive`, `levelOfAssurance`, `profile` and the new `attributeProfiles` from the browser with `login:allowParametersFromRequest` ([login parameters for test SPs](integration.md#login-parameters-for-test-sps)).

**Login** is started by `[Authorize]`, as Forms authentication's `loginUrl` did, or by a link to `/auth/login`.

**Logout** was a link to the logout handler. It is now a form that posts to `/auth/logout` with an antiforgery token; a `GET` is refused. See [logging out](integration.md#logging-out).

## Code

| Legacy                                               | Replacement                                                              |
|------------------------------------------------------|--------------------------------------------------------------------------|
| `Saml20Identity.Current`                             | `User` in a controller or view, or `HttpContext.User`                    |
| `Saml20Identity.IsInitialized()`                     | `User.Identity.IsAuthenticated`                                          |
| `Saml20Identity.Current["name"]`                     | `User.FindAll("name")`, or `User.FindFirst("name")?.Value` for one value |
| `Saml20Identity.Current.HasAttribute("name")`        | `User.HasClaim(c => c.Type == "name")`                                   |
| `Saml20Identity.Current.Name`, `PersistentPseudonym` | `User.Identity.Name`, the NameID                                         |
| `Saml20AttributeQuery`                               | None                                                                     |

Attribute names are unchanged: An attribute such as `https://data.gov.dk/model/core/eid/cprNumber` becomes a claim of that type. [The signed-in user](integration.md#the-signed-in-user) lists the claims the library adds.

## Extensions

| Legacy                                             | Replacement                                                                                                                                                                                  |
|----------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `IAuthnRequestAppender`                            | `IAuthnRequestProcessor`, registered after `AddOioSaml`                                                                                                                                      |
| `IAction.LoginAction`                              | The cookie scheme's `OnSignedIn` event. `SamlPrincipalAction` and `RedirectAction` are built in                                                                                              |
| `IAction.LogoutAction`                             | The cookie scheme's `OnSigningOut` event, which runs for logout from your application and from the IdP                                                                                       |
| `ISessionStoreProvider`, SQL Server session store  | The ASP.NET Core session backed by a shared `IDistributedCache`, such as `AddDistributedSqlServerCache`. See [running more than one instance](integration.md#running-more-than-one-instance) |
| `IAuditLogger`, log4net audit logger               | Route the `DK.Gov.Oio.Saml.Audit` category with any logging provider. See [logging](logging.md)                                                                                              |
| `System.Diagnostics` trace source `dk.nita.saml20` | Log categories under `DK.Gov.Oio.Saml`                                                                                                                                                       |
| `CertificateValidation` specifications             | `ICertificateValidator`                                                                                                                                                                      |
| `IDPSelectionEvent`                                | None                                                                                                                                                                                         |

Set the cookie events on the scheme without replacing its `Events` object, which also enforces the session lifetime:

```csharp
builder.Services.Configure<CookieAuthenticationOptions>(Saml20Constants.AuthenticationScheme, options =>
{
    options.Events.OnSignedIn = context => { /* after login */ return Task.CompletedTask; };
    options.Events.OnSigningOut = context => { /* before the local session ends */ return Task.CompletedTask; };
});
```

## Not carried over

These legacy features have no replacement, because NemLog-in doesn't use them or the OIOSAML profile doesn't allow them:

- **Several identity providers:** IdP selection, the `default` attribute, `idpSelectionUrl`, `IDPSelectionEvent` and common domain cookies.
- **Bindings:** HTTP-POST and HTTP-Artifact for requests, SOAP and SOAP logout. Requests use HTTP-Redirect; logout uses HTTP-Redirect and HTTP-POST.
- **Attribute queries.**
- **SP metadata generation.**
- **OIOSAML 2.**
- **Unsigned assertions**  as per the legacy option `omitAssertionSignatureCheck`.
- **SHA-1 and SHA-512 signatures**
- **AES-CBC encryption**
- **The demo identity provider.** Use NemLog-in's DevTest4 or integration test environment.

## Stricter behaviour

Some responses the legacy library accepted are now refused; see [security](security.md):

- **Assertions must be encrypted, with AES-GCM.** The legacy metadata generator listed AES-256-CBC. Remove it from your metadata, so NemLog-in doesn't encrypt with it.
- **Assertions must be signed** with RSA-SHA256, and only the algorithms of [OIO-ALG-01] are accepted.
- **The session lifetime is enforced:** at most 50 minutes idle, and 8 hours in total.
- **IdP certificates are checked for revocation** by the library itself, with OCSP and then CRL. The server must reach OCES OCSP responders and CRLs.
- **IdP metadata** is read on every use instead of watched for changes. A replaced file takes effect without a restart.

## Switching over at NemLog-in

The service keeps its entity ID, but its endpoint URLs change and its metadata must drop AES-CBC, so NemLog-in needs new SP metadata. NemLog-in Administration lets you upload it with an activation time, as for a [certificate change](certificates.md#replacing-the-service-provider-certificate):

1. Write the new SP metadata: Consider whether to conserve entity ID and certificate, `AssertionConsumerService` at `{server}/auth/AssertionConsumerService`, `SingleLogoutService` at `{server}/auth/logout`, and only AES-GCM encryption methods. The sample's [metadata files](../samples/DK.Gov.Oio.Saml.TestServiceProvider/Metadata) are templates.
2. Upload it in NemLog-in Administration with an activation time of your choice.
3. At the activation time, deploy the migrated application.

Between activation and deployment, logins fail: NemLog-in sends responses to URLs the old application doesn't serve. Deploy as close to the activation time as you can.
